# 4라운드 심사 의견 — 심사자 C

## 1. 요약

1. 본 논문은 서울 6호선 규정 질의에서 직접 검색 근거를 보존하고, 관리자가 연결한 규정–길라잡이 구간 링크로 근거를 확장하는 방법을 평가한다.
2. 저자는 선택적 링크 재정렬을 부차 분석으로 두고, 링크 확장 방식 둘을 링크 없는 `hybrid_rerank`와 비교해 검색 Recall 및 링크 정답 Recall의 상승을 보고한다.
3. 다만 그래프 사례 다수가 평가 대상 링크에서 초안되었고 정답 검수도 남아 있어, 현재 수치는 독립적인 현장 질의에서의 성능 향상을 입증하지 못한다.

## 3. 반드시 고쳐야 할 점 (Must-fix)

1. **위치: §3 평가셋 설명, 표 1·3, §4 결론 — 링크 기반 사례 구성과 결론 범위.**

   **문제:** `hybrid_rerank`는 링크 확장의 영향을 분리하는 적절한 기준선이며, 이번 초안은 이전의 미완료 실행 문제를 해결했다. 요약 결과상 링크 두 변형은 그래프 20건에서 이 기준선보다 Recall을 0.253–0.264, 링크 정답 Recall을 0.475–0.517 높인다. 그러나 그래프 20건 중 15건은 승인 링크 36개 가운데 고른 서로 다른 15개 링크의 양쪽 원문을 바탕으로 작성한 LLM 초안 사례이고, 나머지 5건은 개발 자료다. 따라서 이 평가는 링크가 이미 정답 구간과 연결된 사례를 따라가는 능력은 보여도, 실제 질문에서 링크가 맞는지 또는 링크 확장이 필요했는지를 검증하지 않는다. (근거: `paper/data/README.md`, `paper/experiments/summary/notes.md`, `paper/experiments/summary/main_table.md`)

   **수정 요구:** 링크 목록을 먼저 정하지 않은 운영 규정 질의로 별도 그래프 시험셋을 만들고, 규정 실무자가 질문과 필수 근거를 확정한 뒤 같은 `hybrid_rerank`·`link_all`·`proposed` 조건을 비교하라. 새 독립 시험셋을 만들 수 없다면 현재 비교를 “링크 구성 사례에 대한 파이프라인 점검”으로 한정하고, 철도 질의 전반의 성능 향상으로 일반화하지 말라.

2. **위치: §3 평가셋·표 1–3, §4 논의 — 정답의 타당성과 통계 단위.**

   **문제:** 평가셋 v3의 `llm_drafted` 20건(문서형 5건, 그래프형 15건)은 질문·답·근거 위치가 모두 사람 검수 전이다. 특히 그래프 사례에서 링크 양쪽 끝이 답에 모두 필요한지 확인되지 않았다. 또한 집계 메모는 일부 질의가 규정이나 링크를 공유한다고 밝히지만, paired 차이의 부트스트랩과 Wilcoxon 검정은 사례를 단위로 계산한다. 정답 오류와 사례 간 의존을 그대로 둔 채 20건의 p값을 결과의 확실성처럼 해석해서는 안 된다. (근거: `paper/data/README.md`, `paper/data/human_review_checklist.md`, `paper/experiments/summary/notes.md`, `paper/experiments/summary/main_table.md`)

   **수정 요구:** 운영 규정 실무자 2명이 20개 신규 사례의 질문·기준 답·근거 구간을 독립 대조하고, 그래프 사례는 양쪽 링크 끝점의 필요성도 판단하게 하라. 불일치를 조정하고 수정 건수와 합의 절차를 보고한 뒤 라벨을 고정해 전 지표를 다시 계산하라. 같은 규정·링크를 공유하는 사례는 그룹 단위 재표집·검정으로 분석하거나, 이를 할 수 없다면 p값을 추론 근거로 쓰지 말고 기술 통계로 한정하라.

3. **위치: §2 링크 정의, §3 재현 조건, §4 한계 — “사람 승인”의 검증 가능성과 링크 스냅샷.**

   **문제:** 논문의 핵심 차별점은 관리자가 승인한 링크를 통제 경계로 삼는다는 점이지만, 누가 어떤 기준으로 승인하며 문서 개정·링크 폐기 때 어떻게 갱신하는지는 제시하지 않는다. 데이터 안내와 초안도 승인 링크의 DB 조회와 15/36 링크 사용은 밝히지만, 실행 시점 링크 스냅샷은 보존하지 못했다고 적는다. 독자는 평가에 쓰인 엣지의 대상·버전과 승인 상태를 재구성할 수 없다. (근거: `paper/data/README.md`, `paper/experiments/summary/notes.md`, `paper/drafts/round3_draft.md` §4)

   **수정 요구:** 승인 역할·최소 승인 기준·문서 버전 변경 시 재검토 조건을 정의하고, 평가 링크의 ID·양 끝 구간·버전·상태를 고정한 스냅샷 식별자 또는 체크섬을 논문이나 보충자료에 남겨라. 이 정보를 확보할 수 없다면 “사람 승인”을 검증된 방법 요건처럼 쓰지 말고, 평가 당시 DB에 존재한 링크를 사용한 것으로 기여와 결론을 좁혀라.

## 4. 고치면 좋은 점 (Should-fix)

- **위치: §3 표 3, §4 선택 재정렬 해석.** 전체 그래프 20건에서 `proposed`와 `link_all`의 Context Precision 차이는 +0.046이지만 Wilcoxon p=.067이다. 신규 그래프 15건만 보면 차이는 +0.025이고 95% 구간은 0을 포함하며 p=.129이며, Recall과 링크 정답 Recall 평균은 오히려 각각 0.022, 0.067 낮다. 전체 차이를 선택 재정렬의 일반적 정밀도 개선으로 읽지 않도록 신규·개발 집합의 짝 비교를 나누어 제시하고 “회복” 표현은 탐색적 관찰로 한정하라. (근거: `paper/experiments/summary/main_table.md`의 paired case-level comparisons)
- **위치: 초록과 §4 결론.** 초안은 링크 기반 검색의 Recall 상승과 답변 정확도의 차이가 거의 없음을 구분하고 있다. 이 구분을 유지하고, 생성과 채점에 같은 `gpt-5.6-luna`를 쓴 RAGAS Answer Correctness를 운영상 정답성의 증거로 표현하지 말라. 독립적인 답변·인용 검수가 없는 상태에서는 검색 근거 회수 결과까지만 결론내려야 한다. (근거: `paper/drafts/round3_draft.md` §3–4, `paper/experiments/summary/notes.md`)

## 5. 추가 실험 제안

링크를 선정 기준으로 사용하지 않은 실제 운영 질의 20~30건을 규정 실무자 2명이 독립 구성·검수하고, 두 사람의 조정된 gold로 `hybrid_rerank`, `link_all`, `proposed`를 동일 조건에서 3회 비교하라. 답변의 절차 순서·수치·출처 인용도 시스템 변형을 가린 채 같은 검수자가 평가해야 링크 검색 개선이 답변 품질로 이어지는지 판단할 수 있다. 사례 구성·검수와 블라인드 채점에 약 3~5인일, 실행에 별도 API 비용이 필요하다. 이 결과가 나오면 승인 링크의 검색 가치와 선택 재정렬의 추가 가치를 분리해 결론을 정할 수 있다.

## 6. 이전 라운드 지적 반영 여부

- **반영:** 이전 리뷰가 지적한 `hybrid_rerank` 미실행과 `link_all`의 부분 실행은 해소됐다. `paper/experiments/summary/notes.md`에 여섯 변형 × 세 반복 모두 37/37건이 완료된 것으로 기록됐고, 초안은 `hybrid_rerank` 대비 링크 확장을 주 기여로 두며 선택 재정렬은 부차 결과로 낮췄다. 관련 연구에는 KG²RAG·CARAG·도시철도 출입문 RAG가 추가됐고, 기존 v2와 LLM 초안 사례도 분리 집계했다.
- **부분 반영:** 새 그래프 15건이 링크에서 만들어져 그 링크 방법에 유리할 수 있다는 점, 이 15건의 라벨 미검수, 동일 생성·평가 모델, 그리고 답변 정확도 차이가 거의 없다는 점을 한계로 밝혔다. 다만 라벨 검수 전의 점수와 전체 그래프 20건 결합 검정은 여전히 주 결과에 남아 있어, 현장 질의로의 일반화와 링크 선택 효과는 입증되지 않았다. (근거: `paper/drafts/round3_draft.md` §3–4, `paper/data/README.md`, `paper/experiments/summary/main_table.md`)
- **미반영:** 승인 역할·기준·개정 및 폐기 절차, 실험 당시 링크 스냅샷·체크섬은 제공되지 않았다. 링크 선택 결과가 없을 때 불완전 답변을 사용자에게 경고하는 기능도 아직 검증되지 않았으므로, 오프라인 근거 검토 지원 및 운전 판단 금지라는 사용 경계를 유지해야 한다. (근거: `paper/drafts/round3_draft.md` §4, `docs/rag-pipeline.md` §4)
